# План frontend и логики HACKALEM AI

## 1. Фокус задачи

Собрать понятный чат на сайте ekt.kz, где пользователь быстро получает ответ по товару и может безопасно перейти к корзине. В качестве продуктового референса используем механику Kasper: свободный запрос, уточнение, подбор, сравнение и переход к покупке. Визуальный бренд проекта — Quant.

Главная идея MVP: **один чат → карточка товара → явное подтверждение → корзина**.

## 2. Пользовательский сценарий

```text
Открыть чат
  ↓
Задать вопрос свободным текстом
  ↓
Получить ответ и карточку товара
  ├─ товар есть → характеристики / сертификат / цена / остаток
  ├─ товара нет → аналог + причина рекомендации
  ├─ вопрос об условиях → оплата / доставка / минимальная партия
  └─ непонятный запрос → уточняющий вопрос
  ↓
Попросить добавить товар
  ↓
Ассистент показывает товар, количество и остаток
  ↓
Пользователь явно подтверждает «да, добавь»
  ↓
Корзина обновляется → появляется ссылка на корзину
```

## 3. Экраны и блоки frontend

### Главный экран

- шапка: логотип, название ассистента, индикатор корзины;
- короткий заголовок и объяснение пользы;
- окно диалога;
- быстрые кнопки: «Наличие», «Характеристики», «Условия покупки»;
- поле ввода и кнопка отправки;
- блок текущей корзины внизу страницы.

### Сообщение ассистента

Поддерживает:

- обычный текст;
- карточки товаров;
- ссылку на сертификат;
- предупреждение «нет в наличии»;
- блок аналога с объяснением;
- предложение подтвердить добавление.

### Карточка товара

Поля: название, артикул, цена, наличие, склад, ключевые характеристики, сертификат и кнопка/подсказка для добавления.

### Корзина

Поля: товар, количество, цена, итоговая сумма, ссылка на оформление. На MVP корзина может быть частью страницы; отдельная страница магазина подключается позже.

## 4. Состояния интерфейса

```text
idle
  └─ sending → waiting
                  ├─ answer
                  ├─ needs_confirmation
  ├─ comparison
  ├─ alternative
  ├─ needs_clarification
                  └─ error

needs_confirmation
  ├─ confirmed → cart_updated
  └─ cancelled / new_question → idle
```

Правила:

1. Во время `sending/waiting` поле ввода и кнопка блокируются, чтобы не отправить дубль.
2. `needs_confirmation` всегда показывает товар, количество и доступный остаток.
3. Только ответ пользователя запускает подтверждение; нажатие на карточку само по себе ничего не добавляет.
4. При ошибке показываем понятный текст и кнопку «Повторить».
5. История сообщений хранится в рамках текущей сессии.

## 5. Логика frontend

### Состояние приложения

```js
{
  sessionId: string,
  messages: Message[],
  products: Product[],
  cart: { items: CartItem[], total: number, checkoutUrl: string },
  status: 'idle' | 'sending' | 'error',
  pendingConfirmation: { sku: string, quantity: number } | null
  comparison: { sku: string, reason: string }[]
}
```

### Отправка сообщения

1. Проверить, что текст не пустой.
2. Добавить сообщение пользователя в историю.
3. Вызвать `POST /api/chat` с `message` и `session_id`.
4. Показать ответ ассистента и карточки товаров.
5. Если сервер вернул `comparison`, показать несколько карточек в режиме сравнения.
6. Если сервер вернул `needs_clarification`, показать уточняющий вопрос и сохранить последние варианты.
7. Если сервер вернул `requires_confirmation`, показать состояние подтверждения.
8. Если сервер вернул `action.confirm_add` после подтверждения, вызвать `POST /api/cart/confirm`.
9. После успешного добавления обновить корзину через `GET /api/cart/{session_id}`.

## 6. API-контракты для frontend

### `POST /api/chat`

Запрос:

```json
{
  "message": "Есть ли автомат ВА47-29 2P C16?",
  "session_id": "session-id"
}
```

Ответ содержит `message`, необязательный массив `products`, `requires_confirmation` и `session_id`.

### `POST /api/cart/confirm`

Запрос:

```json
{
  "session_id": "session-id",
  "sku": "EK-VA4729-C16",
  "quantity": 2
}
```

Важно: frontend не должен вызывать этот endpoint до явного подтверждения пользователя. Backend дополнительно проверяет подтверждение и остаток.

### `GET /api/cart/{session_id}`

Возвращает актуальные `items`, `total` и `checkout_url`.

## 7. План реализации по приоритетам

### P0 — обязательно для демо

- собрать чат и адаптивную мобильную версию;
- реализовать отправку сообщений и состояния загрузки;
- отобразить товар, цену, остаток, характеристики и сертификат;
- отобразить аналог при нулевом остатке;
- отобразить 2–3 варианта и сравнение по цене, остатку и характеристикам;
- сделать обязательное подтверждение добавления;
- обновлять счётчик, состав и сумму корзины;
- показать ссылку на корзину;
- прогнать чек-лист из `docs/DEMO_CHECKLIST.md`.

### P1 — если останется время

- загрузка PDF/JPEG/Excel/Word с отображением статуса;
- казахский язык;
- рекомендации сопутствующих товаров;
- кнопка «Связаться с менеджером»;
- сохранение истории для авторизованного пользователя;
- skeleton/loading-анимации и улучшенная обработка ошибок.

## 8. Разделение работы в команде

| Зона | Ответственный результат |
| --- | --- |
| Frontend UI | layout, чат, карточки, корзина, адаптивность |
| Frontend logic | sessionId, state machine, API-клиент, confirmation flow |
| Backend logic | intent, поиск каталога, аналоги, серверная проверка корзины |
| Data / QA | тестовые товары, сценарии, проверка Must have |
| Pitch | проблема, ценность, demo script, финальная презентация |

## 9. Definition of Done

- пользователь понимает, что спросить, без подсказки команды;
- ответ по существующему товару содержит корректные данные из каталога;
- отсутствие товара приводит к аналогу с объяснением;
- запрос «добавь» без подтверждения не меняет корзину;
- количество нельзя добавить выше остатка;
- после подтверждения видна актуальная корзина и ссылка на оформление;
- сценарий работает на desktop и мобильной ширине;
- в README есть запуск, архитектура и описание данных.
