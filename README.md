# HACKALEM AI — Quant

ИИ-ассистент-консультант для интернет-магазина электротехнической продукции **ТОО «Электрокомплект» (ekt.kz)**.

Проект решает одну конкретную задачу: помочь клиенту быстро понять, какой товар ему подходит, проверить наличие и характеристики, найти аналог и безопасно перейти к покупке — в одном окне чата.

> Главный продуктовый референс по механике — Kasper в Магазине Kaspi: свободный запрос, уточняющие вопросы, подбор, сравнение и объяснение различий. Мы не копируем брендинг, название или интерфейс Kaspi; адаптируем механику под каталог и бизнес-процессы ekt.kz.

---

## 1. Концепция продукта

### Рабочее название

**Quant — ИИ-помощник по электротехнике для ekt.kz.**

### Одна фраза о продукте

Клиент пишет вопрос обычным языком, а ассистент отвечает только по данным каталога, предлагает подходящий аналог при отсутствии товара и добавляет позицию в корзину только после явного подтверждения.

### Референс механики: conversational shopping assistant

Ассистент должен работать не как обычная строка поиска, а как диалоговый подборщик:

- понимает намерение клиента в свободной формулировке;
- задаёт уточняющие вопросы о задаче, бюджете, параметрах и количестве;
- показывает несколько релевантных вариантов;
- сравнивает характеристики в одном формате;
- объясняет разницу простым языком;
- доводит пользователя до конкретной позиции и корзины.

Это адаптация механики Kasper для электротехники: вместо общего маркетплейса — каталог кабеля, низковольтной аппаратуры, светильников, кабеленесущих систем, инструмента, щитов, автоматизации и другой продукции ekt.kz.

### Почему это нужно

Сейчас клиенту приходится искать характеристики, сертификаты, наличие и аналоги вручную либо обращаться к менеджеру. Это замедляет покупку и создаёт поток однотипных вопросов.

Ассистент сокращает путь:

```text
Вопрос клиента → точный ответ по каталогу → подходящий товар → подтверждение → корзина
```

### Ценность

- клиент быстрее принимает решение о покупке;
- снижается вероятность ухода к конкуренту из-за отсутствия ответа;
- менеджеры освобождаются от повторяющихся вопросов;
- рекомендации объяснимы: пользователь видит, почему предложен именно этот аналог;
- бизнес сохраняет контроль: ассистент не оформляет заказ и не меняет корзину самовольно.

## 2. Что входит в MVP

### Обязательная функциональность

1. Ответ по существующему товару: наличие, цена, характеристики и сертификат.
2. Поиск по артикулу, названию и свободному тексту.
3. Предложение минимум одного релевантного аналога при нулевом остатке.
4. Ответы по условиям покупки: оплата, доставка, минимальная партия.
5. Запрос количества товара.
6. Явное подтверждение перед изменением корзины.
7. Серверная проверка остатка и ограничения количества.
8. Прямая ссылка на актуальную корзину/оформление.
9. Адаптивный интерфейс для desktop и mobile.
10. README, архитектура, инструкция запуска и тестовый сценарий.

### Опционально после MVP

- казахский язык;
- рекомендации сопутствующих товаров;
- подключение визуального frontend к уже добавленному backend endpoint загрузки PDF, Excel, Word и JPEG;
- история диалога для авторизованных пользователей;
- эскалация сложного вопроса менеджеру;
- подключение реального API каталога ekt.kz;
- RAG/LLM для более естественного диалога.

## 3. Главный пользовательский сценарий

```text
1. Клиент открывает чат на ekt.kz.
2. Пишет: «Есть ли автомат ВА47-29 2P C16?»
3. Ассистент показывает наличие, цену, характеристики и сертификат.
4. Клиент пишет: «Добавь 2 штуки в корзину».
5. Ассистент отвечает: «Добавить 2 шт.? Остаток — 42 шт.»
6. Клиент пишет: «Да, добавь».
7. Только теперь сервер изменяет корзину.
8. Ассистент показывает обновлённую корзину и ссылку на оформление.
```

### Сценарий отсутствующего товара

```text
Клиент: «Есть кабель ВВГнг-LS 3x2.5?»
Ассистент: «Этой позиции сейчас нет. Можно взять бухту 20 м: совпадает категория и сечение, доступно 12 шт.»
```

Ассистент обязан объяснить рекомендацию, а не просто показать случайный товар.

### Непонятный запрос

Если данных недостаточно, ассистент не придумывает характеристики или наличие. Он задаёт уточняющий вопрос либо сообщает, что нужно обратиться к менеджеру.

```text

│ Backend: ChatService                          │
│ intent → поиск → ответ → подтверждение        │
└───────────────┬─────────────────────┬────────┘
                │                     │
┌───────────────▼────────┐  ┌────────▼─────────┐
│ CatalogService          │  │ CartService       │
│ поиск, остатки, аналоги │  │ проверка, корзина │
└───────────────┬────────┘  └────────┬─────────┘
                │                     │
         products.json       session cart / API ekt.kz
```

### Стек MVP

- **Backend:** Python 3.11+, FastAPI, Uvicorn.
- **Frontend:** HTML, CSS, vanilla JavaScript — минимум зависимостей и быстрый запуск.
- **Data:** JSON-выгрузка с контрактом, совместимым с будущим API партнёра.
- **Deployment target:** локальный запуск для демо; далее — backend API + встраиваемый frontend на ekt.kz.

### База ekt.kz

Визуальная и продуктовая база — текущая логика ekt.kz: каталог, поиск, регионы, корзина, личный кабинет и B2B-сценарии. На главной сайта уже выделены категории «Кабель / Провод», «Светильники / Лампы», «Низковольтная аппаратура», «Кабеленесущие системы», «Изделия для монтажа и инструмент», «Шкафы / Щиты», «Розетки / Выключатели / Коробки», «Автоматизация», «Видеонаблюдение / СКУД / Сигнализация» и другие. Агент должен использовать эти категории и не создавать параллельный каталог.

## 5. Границы ответственности команды

Главное правило: **Backend Dev и Frontend Dev не перетягивают задачи друг у друга и не закрывают чужую зону без согласования.** Каждый отвечает за свой результат, а взаимодействие происходит через зафиксированный API-контракт.

### Frontend Dev — владелец пользовательского опыта

Отвечает за:

- layout чата и корзины;
- desktop/mobile адаптацию;
- отображение сообщений, карточек, аналогов и сертификатов;
- состояние `idle / loading / error / confirmation / cart_updated`;
- `session_id` и историю сообщений в текущей сессии;
- блокировку повторной отправки во время загрузки;
- вызовы API и обработку ответов;
- понятные empty/error/loading состояния;
- доступность: читаемый текст, видимые кнопки, клавиатурная навигация;
- финальную проверку пользовательского сценария в браузере.

### Backend Dev — владелец данных и бизнес-правил

Отвечает за:

- схему каталога и адаптер к JSON/API партнёра;
- поиск товара и подбор аналога;
- классификацию пользовательского запроса;
- ответы по характеристикам, сертификатам и условиям покупки;
- серверную проверку остатков и количества;
- правило явного подтверждения;
- endpoint корзины и ссылку на оформление;
- защиту от прямого несанкционированного изменения корзины;
- обработку неизвестных данных без выдумывания ответа;
- unit/smoke-проверки бизнес-логики.

### Общая зона — только через контракт

Совместно согласуются:

- JSON-формат запросов и ответов;
- названия полей и статусы ошибок;
- тестовые сценарии;
- изменения, которые влияют и на UI, и на API.

Правило работы при изменении API:

1. Backend Dev сначала обновляет описание контракта.
2. Frontend Dev адаптирует клиент под новый контракт.
3. Нельзя молча менять формат ответа и ожидать, что другая сторона «сама разберётся».
4. Если задача блокирует другую сторону, фиксируем блокер и временно используем mock-ответ, но не переносим ответственность за чужую часть.

## 6. API-контракт MVP

### `POST /api/chat`

Запрос:

```json
{
  "message": "Есть ли автомат ВА47-29 2P C16?",
  "session_id": "demo-session-001"
}
```

Ответ по товару:

```json
{
  "session_id": "demo-session-001",
  "message": "Автоматический выключатель ... Наличие: 42 шт.",
  "products": [
    {
      "sku": "EK-VA4729-C16",
      "name": "Автоматический выключатель ВА47-29 2P C16",
      "price": 1850,
      "stock": 42,
      "characteristics": {},
      "certificate": {"name": "...", "url": "..."}
    }
  ]
}
```

Ответ с подтверждением:

```json
{
  "session_id": "demo-session-001",
  "message": "Добавить 2 шт. товара в корзину? Остаток: 42 шт.",
  "requires_confirmation": true,
  "products": [],
  "action": null
}
```

### `POST /api/cart/confirm`

```json
{
  "session_id": "demo-session-001",
  "sku": "EK-VA4729-C16",
  "quantity": 2
}
```

Endpoint должен вернуть ошибку, если нет подтверждения в этой сессии, товар не найден или количество больше остатка.

### `GET /api/cart/{session_id}`

```json
{
  "session_id": "demo-session-001",
  "items": [],
  "total": 3700,
  "checkout_url": "/cart?session_id=demo-session-001"
}
```

## 7. Бизнес-правила и ограничения

### Нельзя

- менять корзину без явного подтверждения клиента;
- оформлять заказ автоматически;
- обещать наличие, цену или доставку без данных каталога;
- предлагать аналог без краткого обоснования;
- принимать или хранить платёжные данные;
- передавать модели прямое право изменять корзину;
- превышать доступный остаток;
- показывать внутренние системные ошибки пользователю.

### Обязательно

- перед добавлением показать название, количество и остаток;
- сервером повторно проверить подтверждение и остаток;
- при отсутствии товара показать минимум один доступный аналог, если он есть;
- сертификат показывать ссылкой или файлом только если он есть в данных;
- при недостатке данных честно сообщать об ограничении;
- сохранять приватность клиентской сессии;
- поддерживать мобильную ширину.

## 8. Данные каталога

Для MVP используется синтетическая выборка в `backend/data/products.json`.

Минимальная схема:

| Поле | Назначение |
| --- | --- |
| `sku` | уникальный артикул |
| `name` | название товара |
| `category` | категория |
| `characteristics` | технические характеристики |
| `certificate` | название и ссылка/файл сертификата |
| `price` | цена |
| `stock` | остаток |
| `warehouse` | склад/город |
| `tags` | слова для поиска и подбора аналогов |

Когда партнёр предоставит API или выгрузку, меняется только слой `CatalogService`; frontend-контракт остаётся прежним.

## 9. Запуск

Требуется Python 3.11+.

```bash
cd backend
python -m venv .venv
source .venv/bin/activate       # Windows: .venv\\Scripts\\activate
pip install -r requirements.txt
uvicorn app.main:app --reload
```

Открыть: [http://127.0.0.1:8000](http://127.0.0.1:8000)

Swagger API: [http://127.0.0.1:8000/docs](http://127.0.0.1:8000/docs)

Backend принимает JPG/PNG/WEBP, PDF, Word, Excel и CSV до 10 МБ через `POST /api/chat/upload` (multipart: `session_id`, `message`, `file`). Для анализа нужен `OPENAI_API_KEY` из `.env.example`; без него backend просит уточнить артикул текстом. Тестовый файл: `backend/data/demo_specification.csv`. `frontend/visual-demo.html` подключён к API и отправляет по одному вложению за запрос.

### Demo-режим интерфейса

В верхней панели прототипа есть переключатель:

- **Базовый ekt.kz** — показывает сайт без новой функции;
- **С Quant** — включает floating-кнопку и встроенную панель ИИ-агента.

Так можно прямо на демо показать, что именно добавляется к существующему сайту: не отдельный новый магазин, а слой помощника поверх каталога, поиска и корзины ekt.kz.

Для тестов:

```bash
pip install -r requirements-dev.txt
pytest tests
```

## 11. Критерии приёмки

| Проверка | Ожидаемый результат |
| --- | --- |
| Существующий артикул | корректные цена, наличие, характеристики |
| Сертификат | рабочая ссылка/файл, если он есть в каталоге |
| Нулевой остаток | доступный аналог и объяснение рекомендации |
| Условия покупки | содержательный ответ по оплате/доставке/партии |
| Добавление без подтверждения | корзина не меняется |
| Добавление после подтверждения | товар появляется в корзине |
| Количество выше остатка | операция отклоняется |
| Ссылка на корзину | ведёт на актуальное состояние |
| Mobile | чат и корзина не ломаются на узком экране |

## 12. План работы команды

### Шаг 1 — Контракт и демо-данные

- Backend Dev фиксирует схему товара и API.
- Data/QA проверяет 5–10 тестовых товаров.
- Frontend Dev использует согласованный mock JSON и не ждёт готового backend.

### Шаг 2 — Вертикальный срез

- один запрос по товару;
- одна карточка;
- один ответ;
- отображение корзины.

### Шаг 3 — Обязательные ветки

- нулевой остаток и аналог;
- условия покупки;
- подтверждение и проверка количества;
- ошибки и loading states.

### Шаг 4 — Полировка

- mobile;
- визуальная иерархия;
- ссылки на сертификаты и корзину;
- демо-репетиция по чек-листу.

### Definition of Done

Проект считается готовым, если:

- frontend работает на согласованном API без ручного вмешательства;
- backend проходит обязательные бизнес-проверки;
- ни одна сторона не зависит от незавершённой внутренней реализации другой стороны;
- 5 обязательных сценариев проходят через UI;
- README и документация позволяют новому участнику запустить проект за 5–10 минут.
